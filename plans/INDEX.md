That puts one real personal-data field on every kiosk, which is stated rather than glossed — `erm-frontend.md`'s minimisation list and `terminal.yaml`'s "contains only non-sensitive data" claim both had to stop being true — and the compensating control is that erasure rides the same delta sync, so a birth date the server has erased survives on no kiosk beyond one sync interval. The limit sits on the **product**, not the category, so rearranging the grid during a busy shift cannot silently un-restrict a drink; a NULL birth date means *anonymized* and refuses anything restricted, with no fail-open branch; the recorded violation keeps the limit as it stood at the sale and does not clear when the drink is later un-restricted; and the terminal never states a member's age — the refusal names what the **drink** requires. The Getränkewart sets that number and still takes 403 from the member roster. **M10** closed the last gap ([#622](https://github.com/dgloeckner/clubbar/issues/622)): M7 recorded the violation and told nobody, and the audit log holding it is `admin`-only — so the Kassenwart, the office the epic names as the recipient, could not learn one had happened. A dashboard alert and a member-free email now reach them, and each violation can be acknowledged individually. The record does not move when it is: the audit entry is immutable and the acknowledgement is a row beside it, so the incident stays on file forever while only the badge goes quiet — which is what keeps the badge worth reading. The club-website Art. 13 notice remains with [#591](https://github.com/dgloeckner/clubbar/issues/591) |

| [Encryption Key Installation Hardening](./2026-08-16-encryption-key-installation-hardening.md) | Implemented (M1–M2 done; 786 backend tests green in the Security/Notifications/Mail scope) | Follow-up to [ADR-0036](../adr/0036-iban-encryption-sealed-box.md), from the question "what if someone installs a new public key and encrypts all IBANs with it?". Two gaps followed from a backend that can seal but never open: `register()` accepted **any** 32 well-formed bytes, so a mistyped public key activated exactly like a generated one and everything sealed afterwards was unreadable until the next export refused the archived key; and a key swap produced no signal that left the panel, because the expiry notifier covers only the 90/30/7 tiers and a key activated today has 365 days on it. Activation now carries the private half as proof — validated by public-key derivation, never trial decryption, wiped once compared — with `PrivateKeyMismatchException` keeping "no such key" (404) apart from "wrong sheet out of the safe" (422); and registering, activating and revoking each queue one outbox message per admin carrying the **full** fingerprint, the only value that distinguishes the club's key from someone else's since the identifier is free text. Neither stops a determined attacker, and the plan says so: proof of possession closes the typo case, mail is what makes the swap visible, and the change that would actually *prevent* it — a second admin approving activation — contradicts [ADR-0015](../adr/0015-authentication-and-authorization-strategy.md)'s flat model and is left as a follow-up |
