# Issue tracker: GitHub

Issues and PRDs for this repo live as GitHub issues (`dgloeckner/clubbar`).

## Use the GitHub MCP server, not `gh`

**There is no `gh` in a Claude Code cloud session** — `gh: command not found`, and
there is no `hub` and no direct GitHub API access either. An agent that follows a
`gh`-shaped instruction fails on its first command. Everything goes through the
GitHub MCP server instead, whose tools are prefixed `mcp__github__`.

Their schemas are not loaded up front: look one up with `ToolSearch`
(`select:mcp__github__issue_read`, or a keyword search) before calling it.

| Operation | Tool |
|-----------|------|
| Create an issue | `mcp__github__issue_write` with `method: "create"` |
| Update an issue, including labels | `mcp__github__issue_write` with `method: "update"` |
| Read one issue | `mcp__github__issue_read` with `method: "get"` |
| Read its comments | `mcp__github__issue_read` with `method: "get_comments"` |
| List issues | `mcp__github__list_issues` (use `fields` to keep the response small) |
| Search issues | `mcp__github__search_issues` |
| Comment | `mcp__github__add_issue_comment` |
| Close | `mcp__github__issue_write` with `method: "update"`, `state: "closed"` and a `state_reason` |

Two things the tools do not infer for you. **`owner` and `repo` are required on
every call** — there is no "current repo" the way `gh` had one inside a clone.
And **every comment you post must end with the attribution footer**, so a reader
can tell it was written by an agent:

```
---
_Generated by [Claude Code](https://claude.ai/code)_
```

Session GitHub access is scoped to the repositories attached to the session, so
these tools reach `dgloeckner/clubbar` and nothing else unless a repository is
added deliberately.

## Labels in use

Reuse this repo's existing label vocabulary when creating or editing issues; don't invent parallel labels:

- **Type**: `bug`, `enhancement`, `documentation`, `question`, `tech-debt`
- **Priority**: `priority: critical` (money-wrong or data-loss; fix first), `priority: high`, `priority: medium`, `priority: low`
- **Area**: `backend`, `admin-frontend`, `terminal-frontend` (Flutter POS terminal app),
  `testing`, `security`, `ux`, `accessibility`, `i18n`
- **Triage**: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`
  — the five canonical roles, described in [triage-labels.md](./triage-labels.md).
  `owner-action` marks work no agent can do because it needs GitHub or claude.ai
  settings access (issue #696 item 1 is the worked example).
- **State**: `in progress`, `duplicate`, `invalid`, `help wanted`, `good first issue`
- **Maps**: `wayfinder:map` and the other `wayfinder:*` labels belong to the
  wayfinder tooling; do not hand-apply them.
- **Dependency pull requests**: `dependencies` and `javascript` are Dependabot's own;
  `blocked-upstream` is ours — see below.

New issues should carry at least a type label, a priority label, and an area label.
Infrastructure and tooling work is `backend` when it touches the PHP side, and
`testing` when it is about the suites or the harness — an issue about the agent
environment itself usually carries both. There is no separate `infrastructure`
area, and one should not be invented for a single issue.

## `blocked-upstream`: a dependency PR nothing here can fix

Most red Dependabot pull requests are ordinary work: react 19 (#618) failed on one
tooltip callback whose types recharts had widened, and a commit fixed it. Some are
not. #620 raised typescript to 7 while `@typescript-eslint` 8.67.0 — the newest
published release — still declares `"typescript": ">=4.8.4 <6.1.0"`, so npm refuses
the tree and no combination of versions in the group resolves. The release that
would fix it has not been published by anyone.

That is what `blocked-upstream` marks: **the branch cannot be made green from this
repository, and the thing it waits for is someone else's release.** A bump that
merely needs a code change here does not get the label; it gets the code change.

Closing such a pull request loses the reasoning and Dependabot opens it again on the
next run. Labelling keeps one pull request as the standing record, with a comment
naming the exact constraint and the condition that clears it.

**Review the label weekly**, after Dependabot's Monday run:

`mcp__github__list_pull_requests`, filtered to the `blocked-upstream` label.

For each one, check whether the blocker has shipped — for a peer range that is one
query, e.g. `npm view @typescript-eslint/parser peerDependencies.typescript` — and
then either:

- **it shipped**: drop the label, comment `@dependabot recreate`, and treat the pull
  request as ordinary work again;
- **it has not**: leave the label, and add a dated line to the comment only if the
  situation changed. Silence is the normal outcome of this sweep.

A pull request that is still blocked after several sweeps is worth a second look at
the constraint itself: pinning the dependency back, or an `ignore` entry in
`.github/dependabot.yml` naming the condition for its removal, may serve better than
a pull request that reopens forever.

## Pull requests as a triage surface

**PRs as a request surface: no.** _(Set to `yes` if this repo treats external PRs as feature requests; `/triage` reads this flag.)_

When set to `yes`, PRs run through the same labels and states as issues, using the pull-request tools:

- **Read a PR**: `mcp__github__pull_request_read` — `method: "get"`, plus `"get_comments"`,
  `"get_diff"` and `"get_files"` for the rest.
- **List external PRs for triage**: `mcp__github__list_pull_requests`, then keep only
  `authorAssociation` of `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, or `NONE`
  (drop `OWNER`/`MEMBER`/`COLLABORATOR`).
- **Comment**: `mcp__github__add_issue_comment` — it takes a PR number too.
- **Label / close**: `mcp__github__update_pull_request`.

GitHub shares one number space across issues and PRs, so a bare `#42` may be either —
try `mcp__github__pull_request_read` and fall back to `mcp__github__issue_read`.

## When a skill says "publish to the issue tracker"

Create a GitHub issue.

## When a skill says "fetch the relevant ticket"

Call `mcp__github__issue_read` with `method: "get"`, then again with
`method: "get_comments"`.

## Wayfinding operations

Used by `/wayfinder`. The **map** is a single issue with **child** issues as tickets.

- **Map**: a single issue labelled `wayfinder:map`, holding the Notes / Decisions-so-far / Fog body. `mcp__github__issue_write` with `method: "create"` and that label.
- **Child ticket**: an issue linked to the map as a GitHub sub-issue — `mcp__github__sub_issue_write`. Where sub-issues aren't enabled, add the child to a task list in the map body and put `Part of #<map>` at the top of the child body. Labels: `wayfinder:<type>` (`research`/`prototype`/`grilling`/`task`). Once claimed, the ticket is assigned to the driving dev.
- **Blocking**: GitHub's **native issue dependencies** are the canonical, UI-visible representation, but **the MCP server exposes no tool for them** and there is no `gh` and no raw API access in a cloud session. So in practice: put a `Blocked by: #<n>, #<n>` line at the top of the child body, which `mcp__github__issue_write` can maintain. A ticket is unblocked when every blocker is closed. Read `has_parent` / `sub_issues_summary` from `mcp__github__issue_read` for the hierarchy half.
- **Frontier query**: list the map's open children with `mcp__github__issue_read` (`method: "get_sub_issues"`), or `mcp__github__list_issues` scoped to the map's task list; drop any with an open issue in its `Blocked by` line, or with an assignee; first in map order wins.
- **Claim**: `mcp__github__issue_write` with `method: "update"` and `assignees` — the session's first write.
- **Resolve**: `mcp__github__add_issue_comment` with the answer, then `mcp__github__issue_write` with `state: "closed"` and a `state_reason`, then append a context pointer to the map's Decisions-so-far.
